## 2. 问题详情与修复

### R1 含中文的文件路径导致进程崩溃

**现象**

```
$ meetmind-cli "多人对话商务座谈会.part11_爱给网_aigei_com.wav" -o output_real
terminate called after throwing an instance of 'std::filesystem::filesystem_error'
  what():  filesystem error: Cannot convert character sequence: Illegal byte sequence
```

进程直接终止，没有任何可用输出。对中文用户而言，这等于**任何中文文件名都无法处理**。

**根因**（三层叠加）

1. 项目约定「`std::string` 承载 UTF-8」；
2. Windows 上 `std::filesystem::path` 的**窄字符构造函数按本地代码页解释字节**，不是 UTF-8；
3. libstdc++（MinGW）在窄→宽转换失败时**抛异常**，且异常发生在 `path` 对象**构造阶段**——
   所以即使调用方写了 `fs::exists(p, ec)`，`ec` 也拦不住，异常照样抛出并 terminate。
4. 更糟的是 `std::ifstream` 的窄字符路径在 Windows 上同样打不开非 ASCII 文件名。

**修复**

新增 `mm/common/path_utils.{h,cpp}`，所有路径进出 `std::filesystem` 必须经过它：

```cpp
fs::path pathutil::fromUtf8(const std::string& utf8) {
#if defined(_WIN32)
    return fs::path(utf8ToWide(utf8));   // 走宽字符，Windows 下唯一可靠的路径
#else
    return fs::path(utf8);
#endif
}
```

- `fromUtf8` 先按 UTF-8 严格解码，失败回退本地 ANSI 代码页（兼容来自命令行的 ANSI 参数）；
- 提供 `exists / isDirectory / createDirectories / rename / listFiles / openInput / openOutput` 等
  封装，**彻底禁止直接 `fs::path(字符串)`**；
- 同步修复 13 个源文件中的全部调用点（json / wav_io / tokenizer / t2s / replay / config /
  asr_factory / pipeline / exporter / session_store / cli / gui）。

**另一个隐藏点**：`main(int argc, char** argv)` 在 Windows 上拿到的是**本地 ANSI 编码**的 argv，
中文参数一路传进来必然是乱码。CLI 改为用 `GetCommandLineW` + `CommandLineToArgvW` 取回宽字符
命令行再转 UTF-8（为此链接 `shell32`）。

**回归验证**：同一个中文文件名，修复后 `exit=0`，四个导出文件的中文名完整保留。

### R2 崩溃被误报为「用户取消」

**现象**：R1 的崩溃进程退出码恰好是 **3**，而 CLI 的退出码契约里 `3 = 用户取消`。
排查时第一反应是「谁取消了？」，实际是进程被 `abort` 掉了。**崩溃被静默伪装成正常取消**。

**根因**：`std::terminate` → `abort()` 在 Windows 上的退出码与业务退出码空间重叠。

**修复**

- 新增 `mm/common/crash_guard.{h,cpp}`：安装 `std::terminate` 处理器，把未捕获异常写进日志后
  以**独立退出码 70** 终止；
- CLI / GUI 的 `main` 用 `runGuarded()` 包一层 try/catch；
- 退出码契约更新为 `0 成功 / 1 运行期错误 / 2 参数错误 / 3 用户取消 / **70 内部错误（含崩溃）**`。

### R3 部署的 MinGW 运行库与编译器版本不匹配

**现象**：执行 `windeployqt` 部署 Qt 运行库之后，`mm_tests.exe` **启动即段错误**（所有套件全崩）。

**根因**：`windeployqt --compiler-runtime` 复制的是 **Qt 安装目录自带**的
`libstdc++-6.dll` / `libgcc_s_seh-1.dll` / `libwinpthread-1.dll`。
Qt 6.7.1 的 `mingw_64` 里那套运行库是 2021 年构建的，与我们的编译工具链（GCC 13.1）不是同一版本：

| DLL | Qt 自带 (md5) | 编译器 (md5) |
| --- | --- | --- |
| libstdc++-6.dll | `44f0f8c8` | `9a297f4a` |
| libgcc_s_seh-1.dll | `a839c13c` | `852051b6` |
| libwinpthread-1.dll | `11e800f4` | `fe078245` |

而 Windows 的 DLL 搜索顺序里 **exe 所在目录优先于 PATH**，于是旧运行库覆盖了正确的那个。

**修复**：新增 `tools/deploy.sh`——先跑 `windeployqt`，再用**编译器自带**的运行库覆盖 Qt 那份，
最后做启动校验（真的运行 `mm_tests.exe` 与 `meetmind-cli --version`）：

```
== 3/3 启动校验 ==
  mm_tests.exe   启动并全量跑通
  meetmind-cli   正常
```

### R4 转写单元内文本分配缺陷

**现象**：9 分钟音频切出 **92 个语音段，其中 60 段（65%）文本为空**；
非空段数（32）恰好等于转写单元数（30）。SRT 字幕全部挤在每段开头，时间轴与文字严重错位。

**根因**：转写单元分组后，单元文本要按成员段分配。原实现是「**先切句，再按句数分配**」：

```cpp
const auto pieces = splitCore(text, ...);
if (pieces.size() == 1) { out[0] = pieces.front(); return out; }  // ← 全部塞给第一段
```

中文 ASR 输出经常整段只有一两个句号、甚至完全无标点。一条长文本只切出 1 句时，
**整段文本都进了第一个成员段，其余成员全为空**。

**后果比「字幕错位」严重得多**：一个转写单元跨多位说话人时，**整段文本被错误地算给第一位说话人**——
对会议纪要工具而言这是致命的语义错误。

**修复**：重写 `SentenceSplitter::splitByWeights()`，改为**按权重直接切字符**：

1. 按各成员段时长把 `[0, 文本长度)` 划成若干目标切点；
2. 切点在目标位置 ±8 个码点内**优先吸附到标点**（句末 > 逗号），找不到标点则按字符硬切；
3. 为后续每个容器至少保留 1 个字符 → **保证不出现空段**；
4. 保证字符总数守恒（不丢字、不重复）。

配套新增 4 个测试，守住的契约是：**不丢内容 / 无空段 / 切点优先落在标点 / 权重大的段拿更多字符**。

**回归验证**：修复后同一份音频，空文本段由 60 段降到 0 段。

### R5 说话人自动估计形同虚设

**现象**：9 分钟真实多人对话被判为「**1 人**，声纹区分度不足」——「多人会议纪要」的核心功能失效。

**根因**：自动估计的实现是「先按绝对阈值聚类，若簇数为 1 再看合并距离跳变」：

```cpp
if (cc.targetClusters == 0 && clustered.clusterCount == 1 &&
    clustered.mergeDistances.size() >= 2) {   // ← 永远为 false
```

而 `cluster()` 在**第一次迭代**就发现「最小簇间距离 > 阈值」时直接 break，一次合并都没发生，
`mergeDistances` 是**空的** → 跳变分析的前提条件永远不成立 → 自动估计的兜底逻辑是死代码。

真实对话的最小簇间距离是 0.383，而默认阈值是 0.35，恰好踩中这个死角。

**修复**：自动模式下改为**先跑一遍「完全合并」拿到完整树状图**，再用跳变分析挑选切点：

```
auto 模式：
  1) targetClusters = 1 跑完全合并 → 得到 n-1 个合并距离（非递减）
  2) estimateClusters() 找「相对增幅最大」的位置 → 保留 n-i 个簇
  3) 按该簇数重新聚类
  兜底：若跳变分析未发现结构，再退回绝对阈值判定
```

同时改进 `estimateClusters()`：只在「结果不超过 maxSpeakers」的区间内搜索，避免把上限钳制当成答案。

**回归验证**：120 秒片段上给出 3 人（此前为 1 人或过度分裂的 8 人）。

### R6 关键词被口语填充词淹没

**现象**：关键词榜为「觉得(17) / 包装(15) / 一个(13) / 这边(10) / 有点(8) / 价格(8) / 现在(8) /
感觉(6) / 明白(5) / 认为(6)」——**12 个关键词里有 8 个是口语填充词**，纪要毫无信息量。

**根因**：停用词表是按书面语整理的，缺口语填充词。这类词在**本文档内**词频极高，
TF-IDF 的词频项反而给它们加分。

**修复**：按实测结果扩充停用词表（245 → 391 条），新增「会议口语高频填充词」一节，
覆盖认知动词、指示代词、程度副词、时间泛词、连接词、应答语、泛化名词。

**取舍原则**（写入数据文件注释）：只收录「在任何主题下都不承载信息」的词；
`问题 / 需求 / 方案 / 成本` 这类可能承载信息的词**一律保留**。

**回归验证**：关键词变为「包装 / 价格 / 不够 / 香味 / 喜欢 / 接触 / 缺点 / 不错」——全部为内容词。

### R7 中值滤波抹掉少数说话人

**现象**：跳变分析正确估计出 2 人，最终结果却是 1 人。

**根因**：标签平滑用的是窗口 3 的**中值滤波**。当某一类说话人只占少数段时，
中值滤波会把它们**整体翻转成邻居的类别**——把合法说话人当成噪声删除。

**修复**：默认改为「**孤立段消除**」（A A B A A → A A A A A），只处理长度为 1 的抖动，
不触碰连续多段出现的类别；中值滤波保留为 `smoothingWindow >= 5` 时的显式选项。

### R9 whisper 在噪声段产生幻觉 （记录在案）

**现象**：音频尾部的环境噪声段被识别为「谢谢。」「谢谢大家。」「(笑)，」——典型的 whisper 幻觉。

**现状**：已把 `noSpeechProb` 导出到 JSON（此前遗漏），便于下游按该字段过滤；
但**未**在流水线中自动过滤，因为「阈值设多少」缺乏标注数据支撑，贸然过滤可能误删真实内容。
**建议**：需要人工复核的场景，按 `noSpeechProb > 0.6` 过滤；本项目在 `risks` 中提示低置信片段。

### R10 自动说话人分离在真实远场录音上不可靠 （已知取舍）

**现状**：本项目的声纹嵌入是 MFCC 统计量（39 维），设计目标就是「轻量、零第三方依赖」。
在真实远场多人录音上：9 分钟整段自动估计给出 1 人；120 秒片段给出 3 人——**不稳定**。

**为什么不换深度声纹模型**：需要 ONNX Runtime + 数十 MB 权重，与「核心库零第三方运行时依赖、
完全离线、可审计」的项目定位直接冲突（见设计文档 ADR-3）。

**给用户的兜底**：`--speakers N` 人工指定人数后结果稳定得多。
文档已在 README 的「已知限制」与设计文档中明确标注，**不是隐藏缺陷**。

### R11 OpenMP 编译缓存陷阱

**现象**：把 `MEETMIND_GGML_OPENMP` 的 `option()` 默认值从 `ON` 改为 `OFF` 并重新 `cmake --build` 后，
最终二进制**仍然带着 OpenMP**（通过 `--list-engines` 可见编译期后端 `OPENMP = 1`）。
而带 OpenMP 的版本在实测中**反而更慢**（见下），等于默认把用户推到一个更差的配置。

**根因（CMake 缓存语义）**：`option()` 只决定「缓存中没有该键时的初值」。一旦 `CMakeCache.txt`
里已经存在 `MEETMIND_GGML_OPENMP:BOOL=ON`，后续任何 `option(… ON/OFF)` 都**改不动它**——
CMake 直接读取缓存里的旧值。我们改的是源码默认值，不是缓存里的值，所以构建结果纹丝不动。

**修复**

1. 重新配置时显式传参覆盖缓存：`cmake -B build … -DMEETMIND_GGML_OPENMP=OFF -DGGML_OPENMP=OFF`
   （ggml 自己的开关是 `GGML_OPENMP`，两层都要关，否则 ggml-cpu 仍会带 `-fopenmp`）；
2. 在 `CMakeLists.txt` 的 `option()` 上方加注释，写明实测结论，避免后人误改回来。

**实测对照（32 逻辑核，whisper base，60 秒片段，RTF 越高越快）**

| 线程数 j | 无 OpenMP | 有 OpenMP | 变化 |
| --- | --- | --- | --- |
| 8 | 13.3s / 4.46× | 14.1s / — | 慢 ~6% |
| 16 | 11.3s / 5.22× | 14.6s / — | 慢 ~29% |
| 24 | 11.2s / 5.27× | 16.3s / — | 慢 ~45% |

**为什么慢**：ggml 已用自带线程池（按 `n_threads` 并行），OpenMP 又叠一层，
线程超额订阅（over-subscription）互相抢核、上下文切换开销反而吃掉收益。

**回归验证**：`--list-engines` 显示编译期后端 `OPENMP = 0`（仅 `SSE3 / REPACK`），单测 149/149 通过。

### R12 转写单元文本切点切断词语

**现象**：真实转写出现「有一个**包。装**大家看一下」——「包装」被句号从中切断成「包」+「装」，
后半句开头成了错别字，会议纪要可读性受损。

**根因**：R4 的修复把长文本按权重切到各成员段，切点优先级是「句末 > 逗号 > 任意位置」。
中文 ASR 输出常整段无标点或标点稀疏，在目标切点 ±8 码点窗口内**找不到任何标点**时，
就退化为**按字符硬切**——此时完全无视词边界，于是把「包装」这类词一刀两断。

**修复**：给 `splitByWeights()` 增加**词边界吸附**。转写前惰性加载分词器（含词典），
把每个 Token 的结束码点标记为「词边界」；切点优先级改为
**句末(3) > 逗号类(2) > 词边界(1) > 任意位置(0)**。
无标点时优先落在词尾，避免把词切断；有标点时标点仍优先（符合阅读习惯）。
分词器加载时机也一并前移：原实现要到纪要阶段才加载，导致转写阶段用不上，现在改为
流水线启动时 `ensureTokenizer()` 就绪，转写与纪要两阶段共享同一实例。

**回归验证**：60 秒样本复查，段内「包装 / 一个 / 这样子」等词均完整保留；
（`胞/装` 类残留仅出现在 ASR 自身在停顿处插入标点的位置，属模型层产物，不在切分器职责内。）

### R13 默认配置下输出全空 （2026-09-18 新增）

**现象**：把默认配置（`language = "auto"`）拿去跑，**批处理与实时转写都输出 0 段 0 字**；
显式加 `-l zh` 则一切正常。也就是说 **工具开箱即用等于不可用**——
而此前所有端到端脚本都显式传了 `-l zh`，因此一直没被发现。

**根因：误用了 whisper.cpp 的 `detect_language` 语义。**

`whisper.cpp` 的 `whisper_full_with_state()` 里：

```cpp
if (params.language == nullptr || strlen(params.language) == 0 ||
    strcmp(params.language, "auto") == 0 || params.detect_language) {
    // ... 跑一次语言检测 ...
    params.language = whisper_lang_str(lang_id);
    WHISPER_LOG_INFO("%s: auto-detected language: %s (p = %f)", ...);
    if (params.detect_language) {
        return 0;          // ← 直接返回：只做语言检测，不转写！
    }
}
```

即 `detect_language = true` 是「**仅检测语言**」模式（供 `whisper_lang_auto_detect` 这类用法），
**不是**「自动识别语言并继续转写」。原实现写成：

```cpp
} else {
    params.language = nullptr;
    params.detect_language = true;    // ← 于是每次调用都在"检测完就返回"
}
```

日志里能看到 9 次 `auto-detected language: zh (p = 0.99)`，
但 `whisper_full_n_segments()` 始终为 0 —— 极易被误读成「模型没识别出内容」。

**修复**：自动模式改为 `language = "auto"` 且 `detect_language = false`：
内部完成检测后赋值 `params.language`，然后**继续解码**。

**回归验证**：默认配置下批处理 10/10 段、208 字；实时转写正常逐句出稿。

**残留差异（如实记录）**：9 分钟全量下，`-l zh` 得非空段 91/92、1849 字；
`-l auto` 得 83/92、1827 字——**关键词/话题/决议/待办完全一致**，差异集中在低置信短段
（自动检测会改变解码起点的内部状态）。因此中文会议**推荐显式 `-l zh`**；
`auto` 作为「不知道语种」时的兜底，不再是「输出全空」的陷阱。

**为什么测试没抓到**：所有端到端命令都带了 `-l zh`；单元测试用的又是 Mock/回放后端。
**默认值路径恰恰没有任何用例覆盖**——这是本次最值得记取的一条教训。

### R14 实时转写器在工作线程内调用 flush/stop 会死锁 （2026-09-18 新增）

**现象**：GUI 实时面板启动后界面卡死无出稿；单独跑 CLI 实时模式却完全正常。

**根因（两处，都是「自己等自己」）**：

1. `flush()` 通过条件变量等待 `pending_ == 0`，而队列是由**工作线程**消费的。
   当 `flush()` 由工作线程自己调用时，没人能再去消费队列 → **永久阻塞**。
   （GUI 面板的转写器归工作线程所有，因此必然走到这条路径。）
2. `stop()` 无条件 `worker_.join()`。从工作线程内调用即 **join 自己**，
   会抛 `resource_deadlock_would_occur`；而 `std::thread` 析构时若仍 `joinable` 会直接 `terminate`。

**修复**

- `flush()`：检测到「当前就是工作线程」时改为**就地消费队列**（新增 `drainInline()`），不再等条件变量；
- `stop()`：检测到「当前就是工作线程」时改用 `detach()`，让线程自然退出；
- 把单任务处理抽成 `processJob()`，供 `workerLoop` 与 `drainInline` 复用，避免两份逻辑漂移。

**回归验证**：GUI 实时面板 60 秒音频（6× 倍速）完整跑完并正常退出，无卡死、无崩溃。

### R15 实时链路的文本规范化缺失 （2026-09-18 新增）

**现象**：实时输出是**繁体且无标点**（「你們喝完以後打一個…」），
与离线导出的纪要文字风格不一致；噪声段还会直接显示 `[BLANK_AUDIO]` 这类占位标记。

**根因**：实时链路当初只做了「ASR → 回调」，没有接入离线流水线的文本后处理；
`[BLANK_AUDIO]` 则是 whisper 对纯噪声的输出习惯，实时按句出稿时会被当成正常内容。

**修复**

- 实时链路补上**与离线同序**的文本后处理：**繁转简 → ITN → 标点恢复**
  （顺序不可调换：ITN 的数词规则基于简体字表），保证「边录边看」与「事后导出」一致；
- 新增占位标记过滤：`[BLANK_AUDIO]` / `[Silence]` / `[Inaudible]` 等按噪声丢弃。

**回归验证**：实时输出为简体带标点（「你们喝完以后打一个我去这边还有一个包装…」）。

## 3. 这一轮暴露的方法论问题

| 教训 | 具体表现 | 对策 |
| --- | --- | --- |
| **测试数据的地域性偏见** | 146 个测试全用 ASCII 路径 → 中文路径崩溃完全没被发现 | 路径相关测试必须覆盖非 ASCII；已补 |
| **合成素材过于干净** | 单元测试用正弦波与合成语音 → 真实噪声下的幻觉、温度回退、口语填充词全部没暴露 | 端到端验证必须用真实录音 |
| **「逻辑看起来对」不等于会执行** | R5 的兜底分支条件永远为假，是典型死代码 | 对每一条兜底路径补一个能真正触发它的用例 |
| **第三方工具会引入新问题** | `windeployqt` 把不匹配的运行库带进来，是它自己"正常工作"的结果 | 部署后必须做启动校验，不能假设部署成功=可运行 |
| **退出码也是接口** | abort 的退出码与业务退出码撞车，导致崩溃被误读 | 为崩溃保留独立退出码空间（70） |
| **优化必须实测** | OpenMP「看起来应该更快」，实测慢 6%–31% | 任何性能改动都要有对照实验数据 |
| **CMake 缓存会"吞掉"默认值** | 改 `option()` 默认值为 OFF，重新构建后二进制仍带 OpenMP | 改开关默认值必须同步 `-DXXX=OFF` 覆盖缓存，并以 `--list-engines` 核验编译期后端 |
| **切分不能只看标点** | 中文 ASR 常整段无标点，按字符硬切会把词切断 | 切点需在词边界上吸附，分词器应在转写阶段前就绪 |
| **默认值路径必须测** | 所有端到端命令都写 `-l zh`，于是「默认 auto 输出全空」一直没被发现 | 端到端回归至少要跑一遍**不带任何可选参数**的默认调用 |
| **第三方 API 的"相近语义"最危险** | `detect_language` 看着像「自动识别语言」，实际是「只检测不转写」 | 引入第三方参数时读一遍其实现分支，不靠命名猜语义 |
| **并发 API 要写清"谁能调"** | `flush()`/`stop()` 在单线程 CLI 下正常，跑到工作线程里就死锁 | 跨线程组件需明确线程归属，或让接口对「自调用」安全 |
