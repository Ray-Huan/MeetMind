## 2. GPU 加速：为什么 MinGW 编不了 CUDA，以及怎么绕过去

### 2.1 根因：nvcc 只认 MSVC

Windows 版 `nvcc` 的宿主编译器**只能是 MSVC（`cl.exe`）**：

```
$ nvcc -o t.exe t.cu
nvcc fatal   : Cannot find compiler 'cl.exe' in PATH
```

而本项目（含 Qt）是 **MinGW-w64 GCC** 工具链。把 MinGW 的 gcc 交给 nvcc 是不被支持的。
同时 **MSVC 编译的 `ggml` 目标文件与 MinGW 代码 ABI 不兼容**，无法「MSVC 编 ggml + MinGW 链静态库」。

本机实际具备的条件（v1.0 判断有误，这里重新核实）：

| 组件 | 版本 / 路径 |
| --- | --- |
| Visual Studio | **2019 Enterprise**，MSVC 工具链 `14.29.30133`（cl 19.29.30154） |
| Windows SDK | `10.0.19041.0` |
| CUDA Toolkit | `12.3`（`nvcc` / `cudart` / `cublas` 齐全） |
| GPU | NVIDIA GeForce RTX 4060 Laptop GPU，compute capability **8.9**，8 GB 显存 |

CUDA 12.3 支持的 MSVC 版本区间覆盖 19.29，因此两者可以配合。

### 2.2 方案：编译成 DLL，用 C ABI 跨编译器对接

```
┌─────────────────────────────┐        ┌──────────────────────────────┐
│  MSVC + CUDA（独立构建）     │        │  MinGW + Qt（主程序，不变）   │
│  whisper.cpp → whisper.dll  │  C ABI │  mm_core → whisper.lib 导入库 │
│  （含 ggml-cuda 后端）       │ ─────► │  （动态链接，运行时加载 DLL） │
└─────────────────────────────┘        └──────────────────────────────┘
```

**为什么可行**：whisper 对外的 `whisper.h` 是**纯 C 接口**（`extern "C"`），
且 Windows x64 上 MinGW-w64 与 MSVC **共用同一套调用约定**（含「大结构体按隐藏指针传参」），
因此跨编译器调用是安全的。项目里 `WhisperCppEngine::Impl` 本来就只依赖这层 C 接口，
**核心库代码一行都不用改**。

构建脚本：`tools/build-whisper-cuda.sh`（自动探测 VS / SDK / CUDA，配置 → 编译 → 落位）。

### 2.3 关键工程细节（都是实际踩过的坑）

| # | 坑 | 现象 | 处理 |
| --- | --- | --- | --- |
| 1 | **沙箱禁止 `cmd.exe`** | 无法调用 `vcvars64.bat` 建立 MSVC 环境 | 手工构造等价的 `INCLUDE` / `LIB` / `PATH` 后走 Ninja |
| 2 | **VS 生成器缺 CUDA 集成** | VS 的 `BuildCustomizations` 下没有 CUDA props | 改用 **Ninja** 生成器（`cl` + `nvcc` 显式指定） |
| 3 | `option()` 缓存陷阱 | 改了默认值却不生效 | 缓存里的旧值优先，必须 `-DXXX=OFF` 显式覆盖（v1.0 也栽过一次） |
| 4 | **头文件路径不全** | `whisper.h:4: fatal error: ggml.h: No such file` | 导入目标必须同时暴露 `include/` 与 `ggml/include/`，且**必须是同一份源码树**（否则结构体布局不一致） |
| 5 | **`gendef` 生成导入库不可靠** | 从 DLL 反推 `.def` 时，whisper.dll 有 4800+ 个 MSVC 修饰的 C++ 符号，`gendef` 解析到一半异常退出，产出的 `.def` **缺失全部 C API 导出**，导入库里没有 `__imp_whisper_*` | 改**直接使用 MSVC 产出的 `whisper.lib`**（MinGW 的 `ld` 能读 COFF 导入库），`gendef`/`dlltool` 仅作回退 |
| 6 | **CUDA 运行库体积陷阱** | 无差别拷贝 CUDA `bin` 会带上 `cublasLt64_12.dll`（**551 MB**） | 按 DLL 的**真实导入表**精确拷贝：`ggml-cuda.dll` 只依赖 `cudart64_12` + `cublas64_12`，**不需要 cublasLt** → 体积从 840 MB 降到 ~290 MB |
| 7 | 编译告警 `C4819` | 源码含非当前代码页字符 | 无害（仅提示），不影响产物 |

### 2.4 实测：GPU vs CPU（whisper small 模型）

**60 秒片段**

| 配置 | 总耗时 | ASR 耗时 | ASR 实时倍率 | 整体实时倍率 | 峰值内存 |
| --- | --- | --- | --- | --- | --- |
| CPU（`-j 16`） | 29.8 s | 29.7 s | 2.09× | 2.01× | 206 MB |
| **GPU（CUDA）** | **1.9 s** | **1.8 s** | **48.31×** | **32.24×** | 453 MB |
| 提升 | **15.7×** | **16.5×** | 23× | 16× | +247 MB |

**9 分钟真实多人座谈（539.9 秒，完整流水线）**

| 配置 | 总耗时 | ASR 耗时 | ASR 实时倍率 | 整体实时倍率 | 峰值内存 |
| --- | --- | --- | --- | --- | --- |
| CPU（`-j 16`） | 1096.2 s | 1095.2 s | 0.49× | 0.49× | 56 MB |
| **GPU（CUDA）** | **14.8 s** | **14.0 s** | **39.92×** | **36.39×** | 509 MB |
| 提升 | **74×** | **78×** | 81× | 74× | +453 MB |

**正确性对照**

| 维度 | 结果 |
| --- | --- |
| 60 秒片段 | 逐段文字**完全一致**，关键词完全一致 |
| 9 分钟全量 | 92 段中 **6 段有用词微差**（如「认得它怎么样**哪**比较好」vs「**哪儿**」、一处仅空白差异、两段位于尾部噪声区的幻觉）；关键词 / 话题 / 决议 / 待办**完全一致** |

差异来自 GPU 与 CPU 的**累加顺序与数值精度不同**（CUDA 路径部分算子用 fp16 计算），
属于浮点非确定性，不是逻辑缺陷；差异集中在**同义词选择**与**低置信/噪声段**。
对会议纪要而言，结构与语义完全一致，可视为等价。

**两点如实记录的观察**：

- CUDA 版 DLL 里 MSVC 侧编译出的 `ggml-cpu` 显示 `OPENMP = 1`（MSVC 默认开 `/openmp`），
  与 MinGW 侧「关闭 OpenMP」的结论不一致。因 GPU 已把重活接走，CPU 只剩梅尔谱与少量回退算子，
  实测未构成瓶颈（39.9× 实时），故未为它单独重编 DLL。
- DLL 侧 `GGML_SYSTEM_ARCH` 探测为 UNKNOWN（Ninja 生成器下 `CMAKE_SYSTEM_PROCESSOR` 为空），
  CPU 后端回退到 generic 实现。同样因 GPU 承担主要算力，影响可忽略。

**显存占用**（small 模型）：`CUDA0 total size = 487 MB`（模型权重 + KV + compute buffer）。
相较 8 GB 显存绰绰有余，后续换 `medium` / `large-v3` 也有余量。

**39–48× 实时意味着什么**：1 小时的会议录音约 **1.5 分钟**转完；
实时场景下推理只占用音频时长的约 2.5%，余量足以支撑更高精度的识别模型。

### 2.5 使用方式

```bash
# 1) 生成 CUDA 版 whisper.dll（首次执行，约 7 分钟；产物约 290 MB）
bash tools/build-whisper-cuda.sh

# 2) 用 GPU 模式构建主程序
bash tools/build.sh gpu

# 3) 校验：应显示 CUDA : ARCHS = 890 且「GPU 推理: 可用」
./build/bin/meetmind-cli.exe --list-engines

# 4) 推理时加 --gpu
./build/bin/meetmind-cli.exe meeting.wav -m models/ggml-small.bin -l zh --gpu
```

```bash
# 实时转写（文件模拟实时流，1× 速率）
./build/bin/meetmind-cli.exe meeting.wav --realtime --gpu -m models/ggml-small.bin -l zh
# 十倍速压测
./build/bin/meetmind-cli.exe meeting.wav --realtime --speed 10 --gpu -m models/ggml-small.bin -l zh
```

**「启用 GPU 推理」开关在哪 —— 默认已开启**

**`useGpu` 默认值为 `true`：只要本构建含 CUDA 后端，音频转写就直接走显卡，无需任何参数。**
未编入 GPU 后端的构建会**静默回退 CPU**（属构建选择而非故障，只记 INFO 日志、不告警）。

| 入口 | 位置 | 说明 |
| --- | --- | --- |
| **命令行（批处理 / 实时）** | `--gpu` / `--no-gpu` | 默认即 GPU；`--no-gpu` 强制 CPU。两个都不给时按配置文件里的 `useGpu` |
| **GUI · 设置** | 菜单「设置」→「识别」页 → **使用 GPU 推理（CUDA）** | 默认勾选（本构建含后端时）；取消勾选即改走 CPU |
| **GUI · 实时转写页** | 「实时转写」标签页 → **使用 GPU 加速（实时建议开启）** | 只作用于实时转写 |
| **配置文件** | `~/.meetmind/config.json` → `"useGpu": false` | 持久化关闭 GPU；CLI 与 GUI 都会读取 |

> 三处 UI 开关口径一致：都反映配置里的 `useGpu`，且在本构建**未编入 CUDA 后端**时自动置灰
> 并给出启用方法（置灰时**不写回**配置，避免把「本构建不可用」误固化下来）。
> 另外 CLI 只在「与预期不符」时出话：构建缺 GPU 后端时说明按 CPU 跑；
> 配置里被关掉时提醒一句——命令行显式 `--no-gpu` 则不劝回。

构建开关：`-DMEETMIND_WHISPER_CUDA_DLL=ON`（接入预编译 CUDA DLL）。
运行时 `whisper.dll` / `ggml*.dll` / `cudart64_12.dll` / `cublas64_12.dll` / MSVC 运行库
会由 CMake 自动复制到可执行文件同目录。

### 2.6 分发体积

| 组件 | 体积 |
| --- | --- |
| `ggml-cuda.dll` | 192 MB（sm_89 全套内核） |
| `cublas64_12.dll` | 94 MB |
| `whisper.dll` + `ggml*.dll` | ~3 MB |
| CUDA / MSVC 运行库 | ~1 MB |
| **合计** | **约 290 MB** |

想压体积可以：① 只编单个架构（当前就是只编 sm_89，如要兼容更多显卡会更大）；
② 不随包分发 CUDA 运行库，改为要求目标机已装 CUDA 并把其 `bin` 加入 `PATH`。

## 3. 实时（流式）语音转写

### 3.1 架构

```
音频源 IAudioSource ──► OnlineVad（增量断句）──► 任务队列 ──► 推理线程 ──► 回调出稿
  ├ FileAudioSource（文件按实时速率模拟，可测）
  └ MicAudioSource （麦克风，GUI 侧实现，同一接口）
```

代码位置：`src/mm/live/`

| 组件 | 职责 | 关键设计 |
| --- | --- | --- |
| `OnlineVad` | 增量语音活动检测 | 自适应噪声底（**瞬时下降 / 缓慢回升**）+ 迟滞（进入 3 帧、退出 60 帧）；门限 = 噪声底 + clamp(0.4×(峰值−噪声底), 5, 18) dB；能量压线时用过零率二次判决 |
| `RealtimeTranscriber` | 流式转写编排 | **采集线程只做缓冲与 VAD，推理在独立工作线程**（否则麦克风回调被阻塞会丢帧）；单工作线程保证「出稿顺序 = 音频顺序」；段长超过 `maxSegmentMs` 强制切段，给时延一个上界 |
| `FileAudioSource` | 文件模拟实时流 | 按「实时速率 × speed」分块推送，用**绝对时刻对齐**避免逐块漂移；`speed` 可做压测 |
| `IAudioSource` | 音频源抽象 | 核心库不依赖 Qt；麦克风实现放在 GUI 层 |

**断句参数**：判句停顿 `--rt-silence` 默认 **600 ms**（会议对话自然停顿约 1.5 s，
600 ms 既能及时断句又不会把句中停顿误判成句末）；单段上限 `--rt-segment` 默认 **12 s**
（连续讲话时保证按固定节奏出稿，而不是等一整段说完）。

### 3.2 时延构成

一次出稿的延迟 = `判句停顿` + `采集块长` + `推理耗时 + 排队`。

| 项 | 实测 |
| --- | --- |
| 判句停顿 | 600 ms（可调） |
| 采集块长 | 100 ms |
| 推理 + 队列 | GPU 下 1 s 音频约 21 ms → 实际观测 **114–762 ms** |

### 3.3 实测（60 秒片段，small 模型，GPU，1× 速率）

```
推理设备: GPU（CUDA）    后端: whisper.cpp（端侧）
实时参数: 判句停顿 600 ms，单段上限 12000 ms，模拟倍速 1×
（音频 01:00，边进边出稿）

[00:00] 你们喝完以后打一个我去这边还有一个包装关于这个包装的是这样子的。      [延迟 552 ms]
[00:09] 这边有一个包装大家看一下有一个包装的一个打分这边就是一个五两页的199火……[延迟 691 ms]
[00:21] 所以你们可以通过你们对他的一个拿分来告诉我……                      [延迟 447 ms]
[00:33] 怎么样去改进这个包装变成什么样的包装我就更喜欢了？                  [延迟 384 ms]
[00:37] 嗯 大家看一下。                                                    [延迟 117 ms]
[00:39] 大家帮我填一下这个小文件啊大家先填一下小文件。                      [延迟 567 ms]
[00:49] 谢谢。                                                            [延迟 261 ms]
```

| 指标 | 结果 |
| --- | --- |
| 音频时长 / 墙钟耗时 | 60.0 s / **60.4 s**（真·实时） |
| 累计推理耗时 | 3.6 s |
| 推理实时倍率 | **16.72×** |
| 出稿延迟 | 平均 **399 ms**，峰值 691 ms |
| 产出 | 9 段 / 683 字节 |

> **为什么实时比离线慢（16.7× vs 48×）**：whisper 无论输入多短都会完整编码一个 30 秒窗口，
> 而实时是「按句出稿」，9 个短句就要付 9 次固定开销；离线把相邻语音合并成 2 个 29 秒单元，
> 只付 2 次。这是**时延换吞吐**的必然结果——16.7× 的余量依然足够支撑实时。

### 3.4 与离线结果的一致性

实时输出**同样经过**「繁转简 → ITN → 标点恢复」三步，且**顺序与离线流水线完全一致**
（顺序不可调换：ITN 的数词规则基于简体字表）。
因此「边录边看的文字」与「事后导出的纪要文字」不会出现繁简/标点不一致。

> 注：GPU 版本实测中，`whisper` 仍会在**纯噪声段**产生幻觉（如「(啪)」「(字幕製作:貝爾)」），
> 这是模型层问题（见 docs/07 R9），实时链路只负责如实呈现。

## 4. CPU 调优（v1.0 实测，仍然有效）

### 4.1 线程数（60 秒片段，whisper base）

| 线程数 | 识别耗时 | 实时倍率 |
| --- | --- | --- |
| 8 | 13.3 s | 4.46× |
| **16** | **11.3 s** | **5.22×** |
| 24 | 11.2 s | 5.27× |
| 32（全部逻辑核） | 17.4 s | 3.43× |

**为什么开满线程更慢**：whisper 的编码器是访存密集型算子，超过物理核数后，
超线程与能效核争抢内存带宽与 L3 缓存，反而拖慢。默认取 `max(2, 逻辑核数/2)` = 16。

### 4.2 转写单元上限（60 秒片段，whisper base，间隔阈值 2500 ms）

| 单元上限 | 识别耗时 | 实时倍率 | 单元数 |
| --- | --- | --- | --- |
| 25000 ms | 14.3 s | 4.17× | 3 |
| **29000 ms** | **12.1 s** | **4.92×** | 2 |
| 29000 ms（间隔阈值改 5000） | 12.0 s | 4.93× | 2 |

**取 29000 ms**：whisper 按固定 30 秒窗口编码，单元做到刚好贴着窗口上界收益最大；
再大就会被窗口边界切开，白做一次编码。间隔阈值保持 2500 ms。

### 4.3 转写单元分组的总收益

| 配置 | 识别耗时 | 整体实时倍率 |
| --- | --- | --- |
| 逐段转写（8 段 → 8 次调用） | 82.4 s | 0.61× |
| 分组后 + 调优（small 模型） | 440.6 s | **1.22×** |

> 同一段 50.5 秒音频：逐段（8 次调用）82.4 s → 分组（2 单元）25.4 s，**提速 3.2 倍**。
> 分组的核心价值不是「更少的数据」，而是**避免重复支付固定开销**：1.2 秒的段与 30 秒的段，
> 编码耗时几乎相同。

### 4.4 OpenMP（60 秒片段，whisper base）

| 线程数 | 未启用 OpenMP | 启用 OpenMP | 变化 |
| --- | --- | --- | --- |
| 8 | 13.3 s | 14.1 s | −6% |
| 16 | 11.3 s | 14.6 s | **−23%** |
| 24 | 11.2 s | 16.3 s | **−31%** |

**为什么更慢**：ggml 自己就用 `n_threads` 起线程池并行矩阵运算；再叠一层 OpenMP，
两套线程池在同一批核心上超额订阅，上下文切换与缓存抖动吃掉了收益。
所以 `MEETMIND_GGML_OPENMP` 默认 **OFF**。

### 4.5 温度回退（120 秒片段，whisper base）

| `--temp-inc` | 识别耗时 | 实时倍率 | 文本相似度 | confidence 中位数 | 空段占比 |
| --- | --- | --- | --- | --- | --- |
| 0.2（默认） | 31.4 s | 3.79× | 基准 | 0.864 | 52% |
| 0（关闭回退） | 21.9 s | 5.43× | 81.0% | 0.698 | 72% |

**如何取舍**：whisper 在解码结果不满足熵/对数概率阈值时会**逐步升高温度重解码**
（0.2 → 1.0，最多 6 次）。嘈杂录音上回退频繁触发，这是识别耗时远超音频时长的主因。
关闭后快 1.43 倍，但置信度明显下降、空段增多——说明部分内容确实是在回退后才解出来的。
**决策：默认保留 0.2**，把 `--temp-inc 0` 作为「只要速度」时的手动选项。

> **GPU 下的新情况**：GPU 上温度回退的成本被大幅摊薄（48× 实时），
> 因此**不再需要为了速度牺牲回退**——这也是 GPU 加速除「更快」之外的实际价值。

## 5. 当前条件下的实用建议

| 场景 | 推荐配置 | 预期效果 |
| --- | --- | --- |
| **有 NVIDIA 显卡（本机）** | `--gpu -m models/ggml-small.bin` | **48× 实时**，质量与 CPU 一致 |
| 要最高质量（GPU） | `--gpu -m models/ggml-medium.bin`（需另下模型） | 显存充足，速度仍远超实时 |
| 无显卡 / 兼容性优先 | `-m models/ggml-small.bin -j 16` | 2.1× 实时 |
| 要速度（CPU） | `-m models/ggml-base.bin -j 16 --temp-inc 0` | 约 5× 实时，适合长会议初筛 |
| **实时字幕 / 边录边看** | `--realtime --gpu -m models/ggml-small.bin` | 出稿延迟 ~0.5 s |
| 声音干净（近场麦） | 默认参数即可 | 分组优化收益最大 |
| 嘈杂远场 | `--temp-inc 0.2`（默认） | 保留回退，尽量多解出内容 |
| 已知人数 | `--speakers N` | 说话人分离比自动估计可靠得多 |

> **关于自动说话人分离**：本项目的声纹嵌入是 MFCC 统计量（轻量、零依赖），
> 在真实远场多人录音上**不可靠**。9 分钟实测：自动估计给出 1–2 人，
> 而人工指定 `--speakers 4` 能给出稳定结果。这是设计文档中已标注的已知取舍，不是隐藏缺陷；
> 要显著改善需引入深度声纹模型（需 ONNX Runtime + 数十 MB 权重，与「零第三方依赖」定位冲突）。
