## 1. 采用的开发流程

按企业内常见的**轻量瀑布 + 迭代**方式推进，每个阶段都有可验收的产物，不做无产物的口头推进：

| 阶段 | 产物 | 验收方式 |
| --- | --- | --- |
| S1 需求分析 | `docs/01-需求规格说明书.md` | 功能/非功能需求可量化，含需求追踪矩阵 |
| S2 系统设计 | `docs/02-系统设计说明书.md` | 架构、模块职责、算法选型理由、性能与安全设计 |
| S3 工程搭建 | `CMakeLists.txt` + 分层目录 | `build.sh core` 零告警通过 |
| S4 增量实现 | `src/mm/**` | 每个模块完成后立即编译 + 补测试 |
| S5 接口固化 | `docs/03-接口文档.md` | 公开 API 与实现一致，包含实现契约 |
| S6 测试 | `tests/**` + `docs/04-测试计划与报告.md` | 全部用例通过，含端到端真实验证 |
| S7 交付 | `README.md` + 全量文档 | 新环境可按 README 从零构建运行 |

**关键做法**

1. **先打通骨架再填充**：先让 CMake + 最小可编译单元跑通，避免"写了 5000 行才发现构建配置错误"。
2. **每完成一层立即编译**：`mm/common` → `mm/audio` → `mm/asr` → `mm/nlp` → `mm/diar` → `mm/pipeline` → `mm/cli` → `mm/gui`，每层编译一次。
3. **测试与实现同批交付**：不攒到最后统一补测试。发现断言与实现不一致时，先判断"是实现错了还是断言错了"，再决定改哪边（本轮的 14 个缺陷中有 10 个是通过这种方式定位的）。
4. **构建开关保证可降级**：`MEETMIND_WITH_WHISPER` / `MEETMIND_BUILD_GUI` 缺失依赖时自动关闭，核心库始终可独立构建与测试。

## 3. 缺陷记录（本轮实际修复）

以下均为开发过程中**真实发现并修复**的问题，而非事后编造。按类型分组。

### 3.1 算法/逻辑缺陷

| # | 位置 | 现象 | 根因 | 修复 |
| --- | --- | --- | --- | --- |
| D1 | `nlp/textrank.cpp` `normalize` | 归一化后最大值达 1.5（应 ≤ 1.0） | `minmax_element` 返回的迭代器指向被原地修改的容器，取值时已被覆盖（别名缺陷） | 先拷贝 `lo`/`hi` 数值再修改 |
| D2 | `audio/segmenter.cpp` `slice` | 转写时间戳整体偏移一个 `padMs`（200 ms） | 切片按 `padMs` 向前扩展，但调用方用 `segment.startMs` 回填时间戳 | 新增 `actualStartMsOut` 出参，流水线使用实际起点 |
| D3 | `nlp/text_normalizer.cpp` | `"100 万"` → `"100 0"`（内容被破坏） | 纯单位词「万」被当成独立数词解析为 0 | 数词串必须至少含一个中文数字字 |
| D4 | `nlp/text_normalizer.cpp` | `"九月二十日前"` 无法识别为日期 | 单个中文数字后跟「月」不参与转换，导致 `extractDueDate` 匹配不到 | 新增「单数字 + 日期/时间量词」转换规则（保守白名单，不含「点」「个」） |
| D5 | `nlp/punctuation_restorer.cpp` | `"我们开始吧"` 被判为疑问句 | 语气词「吧」被列入疑问标记 | 从疑问标记中移除「吧」 |
| D6 | `nlp/action_item_extractor.cpp` | `"这个由李四负责"` 抽出责任人 `"个由李四"` | 向后扫描未把「由/请/让/叫」视为姓名左边界 | 纳入边界字符集 |
| D7 | `nlp/action_item_extractor.cpp` | `"待办是要继续跟进这件事"` 抽出责任人 `"继续"` | 动词/副词短语被当作人名 | 新增"姓名不以功能字/副词开头"判定（88 个前缀字） |

### 3.4 性能缺陷（第二轮实测发现）

| # | 现象 | 分析 | 修复 |
| --- | --- | --- | --- |
| D27 | 50.5 秒音频耗时 107 秒（RTF 0.47×），远低于 NFR-1 要求的 1.5× | 逐个 VAD 语音段调用识别引擎；whisper 无论输入多短都会完整编码一个 30 秒窗口，1.2 秒的段与 30 秒的段耗时几乎相同 → 8 次固定开销 | 新增 `groupSegments()` 转写单元分组 |

> D27 的修复过程本身也踩了一次坑：默认 `mergeGapMs = 1500` 而实测会议语音的自然句间停顿为
> 1.55–1.64 秒，导致**合并根本没触发**，一度观测到"优化后反而更慢"。通过构造 5 组对照实验
> 才定位到真正的阈值拐点（2500 ms），最终把默认值定为 2500 ms 并在代码注释中记录实测依据。
> 教训：**优化必须用对照实验验证，不能凭直觉设参数**。

> 另有 12 处为**测试断言本身写错**（如对 UTF-8 码点数的期望、差分公式的边界行为、孤立节点的 PageRank 收敛值、`slice` 补白后的期望时长、
`normalize` 的常量序列语义、关键词数量上限、分词跳过标点等），已按实现的正确语义修正断言；
另有 1 处因"单个翻译单元过大"触发编译器 ICE，通过拆分测试文件解决。

## 4. 关键工程决策记录（ADR 摘要）

### ADR-1 为什么自研 JSON / 分词 / DSP，而不引入第三方库？

**背景**：需求强调"端侧、可审计、无外联"。第三方二进制依赖会带来分发、许可证与安全审计成本。
**决策**：核心库只依赖 C++ 标准库。JSON（约 400 行）、最大概率路径分词（约 350 行）、FFT/Mel/MFCC（约 400 行）、TextRank/MMR（约 300 行）均自研。
**代价**：需要自己保证正确性——因此为每块都配了单元测试（含逆变换还原、谱峰位置、分词可还原性等强断言）。
**结论**：核心库 `mm_core` 运行时零第三方依赖；唯一的重量级依赖（whisper.cpp）被设计成**可选**且可通过开关关闭。

### ADR-2 为什么 ASR 采用"逐段转写"而非整段喂入？

**理由**：① 内存峰值与"段长"而非"会议时长"相关；② 天然支持按段取消与进度上报；③ 便于把说话人标签直接挂到段落上。
**代价**：段边界处的上下文丢失。**缓解**：切片时向前后各补 200 ms 白，避免切掉字头字尾。

### ADR-3 为什么用 MFCC 统计量而不是深度声纹嵌入？

**理由**：深度声纹（如 ECAPA-TDNN）需要 ONNX Runtime 与数十 MB 权重，与"零第三方依赖、完全离线、轻量"的定位冲突。
**代价**：区分能力弱。**缓解**：① 明确记录为已知限制；② 结果中通过 `degraded` + `note` 显式暴露退化情况；③ 支持人工指定说话人数以兜底。
**结论**：这是一个**已知取舍**，不是隐藏缺陷。

### ADR-4 为什么转写失败要保留占位段？

**理由**：下游（说话人标签、句子、统计）都按索引与转写段对应。若某段失败就跳过，会导致后续全部错位，产生"看似成功实则错乱"的结果。
**决策**：失败段以空文本 + `confidence=0` 占位，并写入日志与风险提示。宁可"少一句"，不可"错位"。

### ADR-5 为什么导出使用"临时文件 + 原子替换"？

**理由**：用户可能在导出过程中关闭程序或磁盘写满。直接写目标文件会留下不完整文件，而用户可能误以为内容完整。
**决策**：写 `<name>.tmp` → `rename` 覆盖；跨设备失败时退化为"删除 + 重命名"。测试中对 `.tmp` 残留做了断言。

### ADR-6 为什么本期不引入生成式摘要？

**理由**：端侧生成式摘要需要额外的模型运行时（数 GB 权重 + 推理框架），与"零第三方依赖"冲突；若实现为 HTTP 客户端，则引入网络代码路径，与"无外联"的安全承诺产生解释成本。
**决策**：把可变部分抽象为 `ISummarizer`，本期交付完全离线的 `ExtractiveSummarizer`，并**用测试证明**自定义后端可以即插即用（`nlp_minutes.自定义摘要后端可插拔`）。配置中不保留任何未实现功能的占位字段。

### ADR-7 为什么要专门做"繁转简"？

**背景**：端到端验证发现 whisper small 对同一段音频会在繁体/简体之间摇摆（约一半句子输出繁体）。
由于 ITN 数词规则、停用词表、关键词词表、待办触发词全部基于简体，繁体输出会导致
关键词漏抽、状态不一致（同一段文本里繁简混用）。

**备选方案**
1. 用 whisper 的 `initial_prompt` 引导输出简体 —— 不可靠，且会占用上下文；
2. 整词替换 —— 依赖分词正确性，分词错就漏转；
3. **字符级映射** —— 与分词无关，鲁棒性最好。

**决策**：采用方案 3。映射表由 `tools/prepare_data.py --t2s` 从 `zhconv` 生成
（对 CJK 基本区与扩展 A 逐码点转换并验证），产出 4303 条单字映射，作为项目数据文件随源码分发。
**效果**：与参考脚本的相似度 76.3% → 94.7%，关键词命中从 0/6 提升到 4/6。

### ADR-8 为什么把"报告定稿"放在导出之前？

**背景**：导出的 Markdown/HTML/JSON 里包含一份处理报告（各阶段耗时、总耗时、识别后端等）。
最初的实现是先导出、再统计耗时，导致**所有导出文件里的总耗时都是 0、文件清单都是空的**。

**决策**：把语义显式化——
- `report.totalMs` 定义为「解码→纪要」的耗时，**不含导出**；
- 导出耗时单列 `report.exportMs`，两者相加才是端到端总耗时；
- `Exporter::planPaths()` 在渲染前算出全部目标路径，产物内即可准确列出"本次写出的文件"。

**理由**：这样所有导出格式拿到的都是同一份**自洽且完整**的报告，无需二次渲染；
代价是 `totalMs` 的语义需要文档明确（已在接口文档与代码注释中标注）。

### ADR-9 为什么把测试拆成 6 个文件？

**背景**：`test_02_nlp.cpp` 增长到 880 行、60+ 个测试注册对象时，GCC 13.1 报
`internal compiler error: Segmentation fault`。

**决策**：按模块职责拆分（common / audio / nlp / asr+diar / pipeline / nlp-lexicon）。
**收益**：既绕过了编译器问题，也让失败定位更直接（文件名即模块名）。
